The previous tutorials loaded a local plugin through a `--patch` overlay. That approach is convenient during development but not how plugins are distributed. This tutorial packages the `hello-plugin` as an installable **bundle**, installs it into a **profile** with `dsh plugin add`, and explains the layer order that determines the final composed configuration.

This tutorial assumes the `dsh` CLI is installed. Complete [Plugin Config](/plugins/plugin-config) first. To use a fresh source checkout, complete the [run-from-source section](https://github.com/deepseek-ai/deepseek-harness#run-from-source) and prefix all `dsh ...` commands with `pnpm`.

## Two Concepts

Installation is built on two distinct concepts. Both are described by a `package.json`, but they carry different manifest keys under the `dsh` field and answer different questions:

| Concept | `package.json` key | Answers |
|---|---|---|
| **Bundle** | `dsh.bundle` | "What does this package contribute?" — a patch file that inserts or overrides plugin rows |
| **Profile** | `dsh.profile` | "Which bundles compose this setup, in what order?" |

A bundle is what you author and distribute. A profile is what a user boots with `dsh --profile <name>`. Nothing is both.

## The Bundle Manifest

Create the package directory at the repository root:

```sh
mkdir -p hello-plugin
```

A bundle has a simple layout:

```
hello-plugin/
├── package.json       # declares dsh.bundle
├── cordis.patch.yml   # the layer applied when a profile lists this bundle
└── index.js           # plugin modules the patch rows reference
```

Create `hello-plugin/package.json`:

```json
{
  "name": "dsh-hello-plugin",
  "version": "0.1.0",
  "type": "module",
  "main": "index.js",
  "files": ["index.js", "cordis.patch.yml"],
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}
```

Create `hello-plugin/index.js` with the plugin entry point:

```js
export const name = 'hello-plugin'

export function apply() {
  console.log('[hello-plugin] plugin loaded!')
}
```

Create `hello-plugin/cordis.patch.yml`. Unlike the `--patch` overlays used in development, rows in a bundle patch reference the package by name rather than a relative source path, so Node resolution finds the installed code:

```yaml
- insert:
    - id: hello
      name: dsh-hello-plugin
```

<Note>
  A package without the `dsh.bundle` declaration still installs, but only as a plain dependency: `dsh plugin` prints a warning and activates no configuration layer. Use that format for library packages that plugin packages import, rather than plugins users enable directly.
</Note>

## The Profile Manifest

A profile directory lives under `$DSH_HOME/profiles/<name>` and holds two files:

- `package.json` — the profile's out-of-tree plugin dependencies (managed by pnpm) plus the `dsh.profile` manifest with its ordered `bundles` list.
- `cordis.patch.yml` — the user's own patch layer, applied after every bundle layer.

You never write a profile manifest by hand. The `dsh plugin` command creates and maintains it, as shown in the next section.

## Install into a Profile

`dsh plugin --profile <name> <args...>` forwards arguments to pnpm in the profile directory, so every pnpm verb works. From the directory containing `hello-plugin`, install the local checkout:

```sh
dsh plugin --profile demo add ./hello-plugin
```

The first use initializes the profile (with `@deepseek-ai/dsh-base` as its first bundle), pnpm links the checkout, and `dsh` appends the bundle to `dsh.profile.bundles` because the package declares `dsh.bundle`. The resulting profile `package.json` looks like:

```json
{
  "name": "dsh-profile-demo",
  "private": true,
  "dependencies": {
    "dsh-hello-plugin": "link:/path/to/hello-plugin"
  },
  "dsh": {
    "profile": {
      "bundles": [
        "@deepseek-ai/dsh-base",
        "dsh-hello-plugin"
      ]
    }
  }
}
```

Verify the composed configuration without booting, then boot:

```sh
dsh --profile demo --dump-config   # shows a "# == dsh-hello-plugin" layer
dsh --profile demo
```

To remove the plugin, run:

```sh
dsh plugin --profile demo remove dsh-hello-plugin
```

This removes both the pnpm dependency and the bundle entry from `dsh.profile.bundles`.

## Layer Order

The effective configuration is built by composing layers over an empty root in this fixed order:

1. **Bundle patches** — each bundle named in the profile's `dsh.profile.bundles` list, in list order. `@deepseek-ai/dsh-base` is always first, followed by each installed bundle in the order it was added.
2. **Profile patch** — the profile's own `cordis.patch.yml`, applied after all bundle layers.
3. **Home patch** — `$DSH_HOME/cordis.patch.yml`, for machine-local preferences shared across every profile.
4. **`--patch` overlays** — each `--patch <path>` flag in argv order, applied last.

Later layers win per row. A patch **replaces** an entire row's `config` value rather than deep-merging individual keys. Two practical consequences for bundle authors:

- Your patch can override a row from an earlier layer by matching its `id` — the same mechanism `dsh-web-app` uses to override rows from `dsh-base` — but you must restate every key the row needs, not just the changed one.
- Users can override your rows in their profile's `cordis.patch.yml` without modifying your package, so prefer conservative defaults in your patch and let the schema carry the rest.

In-box bundle names (those under `@deepseek-ai/`) always resolve from the dsh installation itself. pnpm manages only out-of-tree packages, so your bundle can rely on `@deepseek-ai/dsh-base` being present and current.

## Installing from GitHub

Publishing to a registry is not required — users can install directly from a git host:

```sh
dsh plugin --profile demo add github:you/hello-plugin
```

However, a git install fetches sources, not built artifacts: nothing runs your `build` script, so a TypeScript package arrives without its compiled output and fails to load. Two things must be in place:

- **The author** ships a `prepare` script. pnpm runs it after a git install. It must build the published entry points self-contained — it must not assume dev-only context such as a sibling monorepo checkout.
- **The user** allowlists the build. pnpm ≥10 refuses to run a git dependency's `prepare` script until explicitly allowed. `dsh` points at the fix when the first `add` fails: copy the package key into the profile's `pnpm-workspace.yaml`:

  ```yaml
  allowBuilds:
    dsh-hello-plugin: true
  ```

  Then re-run the `add` command.

<Warning>
  Allowlisting a build script is permission to execute that package's code on your machine at install time, outside any sandbox the agent runs under. Only allow packages whose source you trust, and pin a commit hash (`github:you/hello-plugin#<sha>`) so a later push cannot silently change what runs.
</Warning>

If you would rather not ask users for the allowance, distribute built artifacts instead:

- **Publish to npm** with the `lib/` directory built at `pnpm publish` time. Users run `dsh plugin add your-package` and receive prebuilt code.
- **Ship a tarball** from `pnpm pack`. Users run `dsh plugin add ./hello-plugin-0.1.0.tgz`.
