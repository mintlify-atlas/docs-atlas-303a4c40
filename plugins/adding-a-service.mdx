When a capability is general enough to need replaceable providers — such as Bash execution, filesystem access, or session persistence — DeepSeek Harness separates the capability into three distinct roles. This three-role pattern gives you swappable backends without changing the tool or the consumers that depend on it.

Complete the [basic plugin tutorials](/plugins/first-plugin) and [plugin lifecycle concepts](/plugins/plugin-lifecycle) before working through this guide.

## Concept Reference

Every replaceable capability in dsh consists of three roles:

| Role | Responsibility |
|---|---|
| **Service Definition** | Defines the Cordis service class and owns the request/result types. Declares `ctx.<key>`. |
| **Service Provider** | Implements the abstract service and registers itself into the Cordis context. |
| **Consumer** | Injects `ctx.<key>` and uses the service — without knowing which provider is active. |

No individual role is a seam. The complete capability — definition + provider + consumer — is the seam.

<Tip>
Put the roles in separate packages only when they need to evolve or be replaced independently. A simple tool plugin that owns its own execution does not need this split. Preemptive decomposition adds package management overhead for no gain.
</Tip>

## When to Use a Seam

Use the three-role pattern when:

- You need **replaceable providers** at deployment time (e.g., local vs. remote execution, different storage backends, different sandbox strategies).
- The **Service Definition and Consumers change rarely** after callers depend on their contract, but providers improve performance or security independently.
- You want to **decouple dependencies**: the Service Provider depends on the Service Definition; the Consumer depends on the Service Definition; the Service Provider and Consumer do **not** depend on each other.

## The Bash Example

The Bash execution capability in dsh is the canonical three-role seam:

- **Service Definition** (`dsh-shell`) — defines the Cordis service and Bash request/result types
- **Service Provider** (`dsh-bash-local`) — executes commands on the local machine
- **Consumer** (`dsh-tool-bash`) — exposes the capability as a model-callable tool

```
┌─────────────┐     ┌──────────────────┐     ┌──────────────┐
│  dsh-shell  │────▶│  dsh-bash-local  │     │ dsh-tool-bash│
│(definition) │     │    (provider)    │     │(consumer/tool)│
└─────────────┘     └──────────────────┘     └──────────────┘
       ▲                                            │
       └────────────────────────────────────────────┘
                    inject: ['shell']
```

Swapping `dsh-bash-local` for a sandboxed provider (`dsh-bash-sandbox`) or a remote provider requires changing one line in `cordis.yml`. The Service Definition and `dsh-tool-bash` remain untouched.

## Tutorial: Develop a Three-Role Capability

<Steps>
  <Step title="Write the Service Definition">
    The Service Definition package owns the Cordis service class and the request/result types. It extends `Service` from `@deepseek-ai/cordis` and augments the `Context` interface so consumers can inject it by key.

    ```ts
    // packages/my-cap/my-cap/src/index.ts
    import { Service, type Context } from '@deepseek-ai/cordis'

    declare module '@deepseek-ai/cordis' {
      interface Context {
        myCap: MyCapService
      }
    }

    export abstract class MyCapService extends Service {
      constructor(ctx: Context) {
        super(ctx, 'myCap')
      }

      /** Execute the capability. */
      abstract execute(request: MyCapRequest): Promise<MyCapResult>
    }

    export interface MyCapRequest {
      input: string
    }

    export interface MyCapResult {
      output: string
    }
    ```

    The abstract `execute` method is the contract that every provider must fulfill. Consumers import only this package — they never import a concrete provider.
  </Step>

  <Step title="Write a Service Provider">
    A Service Provider extends the abstract service class and implements the abstract method. It registers itself via `ctx.plugin(MyCapLocal)`, which makes `ctx.myCap` available to any consumer that injects it.

    ```ts
    // packages/my-cap/my-cap-local/src/index.ts
    import type { Context } from '@deepseek-ai/cordis'
    import { MyCapService, type MyCapRequest, type MyCapResult } from '@deepseek-ai/dsh-my-cap'

    class MyCapLocal extends MyCapService {
      async execute(request: MyCapRequest): Promise<MyCapResult> {
        // Local provider behavior.
        return { output: request.input.toUpperCase() }
      }
    }

    export const name = 'my-cap-local'

    export function apply(ctx: Context) {
      ctx.plugin(MyCapLocal)
    }
    ```

    The provider depends on the Service Definition package. It does not depend on any consumer package.
  </Step>

  <Step title="Write a Consumer">
    A Consumer injects both `tools` and the service key (`myCap`), then uses `ctx.myCap` inside `execute`. It depends on the Service Definition package — never on a concrete provider.

    ```ts
    // packages/my-cap/tool-my-cap/src/index.ts
    import type { Context } from '@deepseek-ai/cordis'
    import { defineTool } from '@deepseek-ai/dsh-tools'

    export const name = 'tool-my-cap'
    export const inject = ['tools', 'myCap']

    export function apply(ctx: Context) {
      ctx.tools.register(defineTool({
        name: 'my_cap',
        description: 'Execute my capability.',
        parameters: {
          input: { type: 'string', required: true },
        },
        output: {
          schema: { type: 'string' },
          render: (_args, value) => [{ type: 'text', text: value }],
        },
        async execute(args) {
          const result = await ctx.myCap.execute({ input: args.input })
          return result.output
        },
      }))
    }
    ```

    Because `inject` declares `'myCap'`, Cordis will not start this plugin until a provider has registered `ctx.myCap`. The consumer and provider never import each other.
  </Step>
</Steps>

## Selecting a Provider via cordis.yml

Load the provider and consumer in `cordis.yml`. To swap providers, replace the provider row — the Service Definition and consumer remain unchanged:

```yaml
# Local execution
- name: '@deepseek-ai/dsh-my-cap-local'
- name: '@deepseek-ai/dsh-tool-my-cap'
```

```yaml
# Replace with a different provider (e.g., remote execution)
- name: '@deepseek-ai/dsh-my-cap-remote'
- name: '@deepseek-ai/dsh-tool-my-cap'
```

This is the same pattern used by `dsh-bash-local` / `dsh-bash-sandbox` for Bash, `dsh-session-persistence-jsonl` / `dsh-session-persistence-sqlite` for persistence, and every other swappable capability in the harness.

## Hook Plugins: Permission Gate Example

A hook plugin intercepts a named extension point on the Cordis event bus without belonging to any specific capability seam. The permission gate below uses `tools/pre-execute` to allow or deny tool calls based on a policy check:

```ts
import type { Context } from '@deepseek-ai/cordis'
import type { PreToolDecision, ToolExecution } from '@deepseek-ai/dsh-tools'

declare function isAllowed(exec: ToolExecution): Promise<boolean>

export const name = 'permission-gate'

export function apply(ctx: Context) {
  ctx.on('tools/pre-execute', async (exec, next): Promise<PreToolDecision> => {
    if (!(await isAllowed(exec))) {
      return { kind: 'deny', reason: 'Denied by policy.' }
    }
    return next()
  })
}
```

The `tools/pre-execute` waterfall is the reorderable policy layer. Each listener either returns a typed decision (`allow`, `deny`, `ask`) or calls `next()` to pass to the next listener. The full set of extension points and when to use each:

- `tools/pre-execute` — allow/deny/ask policy; the waterfall is reorderable
- `ctx.tools.guard()` — monotonic final denial that no later listener can undo
- `tools/execute` — wrap the actual dispatch lifetime (timeouts, retries, metrics); only `exec.signal` is replaceable
- `tools/post-execute` — explicit result transformation, attaching model-facing context, or blocking results
- `tools/result` — contained observation of the immutable final outcome; no mutations

Hook plugins are not inherently permission gates — they can intercept any documented extension point in the harness. A "native hook" is an ordinary Cordis plugin on an interception point; it needs no external protocol.
